## معرفی پروژه

**HSECORE** یک سامانه تحت وب برای یکپارچه‌سازی اطلاعات و فرایندهای ایمنی، بهداشت حرفه‌ای و محیط زیست است. ساختار رابط کاربری راست‌چین و فارسی طراحی شده و امکانات مدیریتی، ثبت اطلاعات، گردش کار، گزارش‌گیری و پیکربندی سامانه را در کنار هم قرار می‌دهد.

این README راهنمای آشنایی با ساختار پروژه، اجرای توسعه، استقرار با Docker، پیکربندی پایگاه داده، عملیات نگهداری و بررسی اولیه خطاهاست.

> **وضعیت و دامنه راهنما:** وجود یک ماژول در پیکربندی رابط کاربری لزوماً به معنی تکمیل همه قابلیت‌ها، آزمون انتهابه‌انتها یا تأیید آمادگی عملیاتی آن نیست. قابلیت‌های موردنیاز باید در نسخه مستقرشده آزمون پذیرش شوند.

## معماری و فناوری‌ها

فناوری‌های قابل مشاهده در فایل‌های پروژه عبارت‌اند از:

- **Frontend:** React، TypeScript، Vite، Material UI و Tailwind CSS
- **Backend:** Node.js و Express
- **Database:** PostgreSQL
- **Database access / migrations:** Drizzle ORM و ابزارهای مهاجرت مرتبط
- **Workflow:** مؤلفه‌های BPMN و SDK مرتبط با Camunda
- **Realtime:** Socket.IO
- **گزارش و نمودار:** Chart.js و Recharts
- **نقشه و داده‌های مکانی:** Leaflet و MapLibre
- **استقرار تولید:** Docker، Docker Compose و فایل `Dockerfile.prod`

فایل `docker-compose.server.yml` پیکربندی برنامه را با نام سرویس `hse-app` و پورت داخلی `3000` تعریف می‌کند. سرویس PostgreSQL کانتینری در همان فایل با پروفایل اختیاری `container-db` تعریف شده است؛ در حالت عادی، پیکربندی برنامه برای اتصال به پایگاه داده میزبان از `host.docker.internal` استفاده می‌کند.

## اجرای توسعه محلی

مخزن را دریافت و وارد مسیر آن شوید:

```bash
git clone https://github.com/aghasiroos/HSECORE-01.git
cd HSECORE-01
```

وابستگی‌ها را نصب کنید:

```bash
npm install
```

فایل نمونه محیطی پروژه را بررسی کنید. اگر `.env.example` وجود دارد، از آن یک فایل `.env` بسازید و فقط متغیرهای موردنیاز را تنظیم کنید. در غیر این صورت، متغیرهای موردنیاز را از کد و تنظیمات سرور استخراج کنید؛ نام یا مقدار متغیرها را حدس نزنید.

اجرای سرور توسعه:

```bash
npm run dev
```

ساخت نسخه تولید:

```bash
npm run build
```

اجرای نسخه تولید ساخته‌شده:

```bash
npm start
```

> `npm start` به خروجی ساخته‌شده در `dist/server.cjs` نیاز دارد. فرمان `npm run lint` در `package.json` فعلی در واقع TypeScript را با `tsc --noEmit --skipLibCheck` بررسی می‌کند؛ این فرمان به‌تنهایی معادل اجرای ESLint نیست.

## نصب و استقرار با Docker

### ۱. نصب Docker روی Ubuntu

به‌روزرسانی بسته‌ها و نصب ابزارهای پایه:

```bash
sudo apt update
sudo apt install -y ca-certificates curl git
```

افزودن مخزن رسمی Docker:

```bash
sudo install -m 0755 -d /etc/apt/keyrings

sudo curl -fsSL \
  https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc

sudo chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update

sudo apt install -y \
  docker-ce \
  docker-ce-cli \
  containerd.io \
  docker-buildx-plugin \
  docker-compose-plugin

sudo systemctl enable --now docker
```

بررسی نصب:

```bash
sudo docker --version
sudo docker compose version
sudo systemctl status docker --no-pager
```

اگر حساب کاربری به گروه `docker` اضافه شود، دسترسی آن عملاً بسیار نزدیک به دسترسی root است. در سرور عملیاتی می‌توان به‌جای این کار از `sudo docker ...` استفاده کرد.

### ۲. دریافت مخزن

```bash
sudo mkdir -p /opt/HSECORE
sudo chown "$USER":"$(id -gn)" /opt/HSECORE
cd /opt/HSECORE

git clone https://github.com/aghasiroos/HSECORE-01.git .
```

اگر پروژه از قبل در مسیر موجود است، `git clone` را دوباره اجرا نکنید. ابتدا وضعیت فایل‌ها و شاخه را بررسی کنید:

```bash
git status
git branch --show-current
git log -1 --oneline
```

### ۳. بررسی فایل‌های استقرار

فایل‌های مهم برای استقرار فعلی:

- `docker-compose.server.yml` — تعریف سرویس برنامه و پایگاه داده اختیاری
- `Dockerfile.prod` — ساخت تصویر چندمرحله‌ای تولید
- `.env` — متغیرهای محیطی و اسرار محلی
- `data/uploads/` — مسیر میزبان برای فایل‌های بارگذاری‌شده برنامه

وجود فایل‌ها را بررسی کنید:

```bash
ls -la Dockerfile.prod docker-compose.server.yml
```

پیکربندی Compose را بدون نمایش اسرار اعتبارسنجی کنید:

```bash
docker compose -f docker-compose.server.yml config -q
```

اگر فرمان خطا داد، پیش از ادامه، متغیرهای مفقود و ساختار فایل Compose را اصلاح کنید.

### ۴. ساخت فایل محیطی امن

فایل `.env` باید در مسیر استقرار ایجاد شود و در Git ثبت نشود. مخزن فعلی `.env*` را در `.gitignore` نادیده می‌گیرد، اما همچنان لازم است از ارسال دستی فایل به مخزن جلوگیری شود.

```bash
cd /opt/HSECORE
touch .env
chmod 600 .env
nano .env
```

متغیرهای مورد استفاده در `docker-compose.server.yml` شامل این موارد هستند:

| متغیر | کاربرد |
|---|---|
| `APP_VERSION` | برچسب نسخه برنامه در ساخت تصویر |
| `BUILD_ID` | شناسه ساخت |
| `RELEASE_ID` | شناسه انتشار |
| `DOCKER_BIND_IP` | آدرس میزبان برای انتشار پورت؛ مقدار پیش‌فرض `127.0.0.1` است |
| `APP_INTERNAL_PORT` | پورت میزبان برای اتصال به پورت داخلی برنامه |
| `SQL_HOST` | میزبان پایگاه داده |
| `SQL_PORT` | پورت پایگاه داده |
| `SQL_USER` | کاربر پایگاه داده |
| `SQL_PASSWORD` | رمز کاربر پایگاه داده |
| `SQL_DB_NAME` | نام پایگاه داده |
| `SQL_SSL` | فعال یا غیرفعال بودن SSL برای اتصال پایگاه داده |
| `SQL_SSL_CA` | گواهی CA، در صورت نیاز به اتصال TLS |
| `JWT_SECRET` | کلید محرمانه امضای توکن‌ها |
| `GEMINI_API_KEY` | کلید API برای قابلیت‌های متکی به Gemini، در صورت استفاده |
| `FORECA_API_KEY` / `FORECA_API_TOKEN` | اعتبارنامه‌های سرویس Foreca، در صورت استفاده |

**هشدار امنیتی مهم:** در فایل Compose فعلی، مقدار پیش‌فرض `SQL_PASSWORD` یک رمز ثابت و ناامن است. در استقرار واقعی حتماً مقدار آن را در `.env` با رمز قوی و یکتا جایگزین کنید. همچنین `JWT_SECRET` و هر کلید API موردنیاز باید با مقادیر معتبر و محرمانه تنظیم شوند. از رمز پیش‌فرض یا مقدار نمونه در محیط عملیاتی استفاده نکنید.

نمونه زیر فقط ساختار تنظیمات را نشان می‌دهد؛ مقادیر داخل علامت‌های `<...>` جایگزین واقعی نیستند و باید با مقادیر امن و متناسب با محیط شما جایگزین شوند:

```dotenv
APP_VERSION=2.6.0
BUILD_ID=production
RELEASE_ID=release-001

DOCKER_BIND_IP=127.0.0.1
APP_INTERNAL_PORT=3000

SQL_HOST=host.docker.internal
SQL_PORT=5432
SQL_USER=hse_user
SQL_PASSWORD=<REPLACE_WITH_A_UNIQUE_STRONG_PASSWORD>
SQL_DB_NAME=hsedb
SQL_SSL=false
SQL_SSL_CA=

JWT_SECRET=<REPLACE_WITH_A_LONG_RANDOM_SECRET>

GEMINI_API_KEY=
FORECA_API_KEY=
FORECA_API_TOKEN=
```

مقادیر واقعی را در README یا Git وارد نکنید. در صورت استفاده از سرویس‌های خارجی، کلیدها را فقط در صورت نیاز پیکربندی کنید.

### ۵. انتخاب روش پایگاه داده

فایل Compose فعلی دو الگوی اتصال را فراهم می‌کند:

**حالت A — PostgreSQL روی میزبان**

این حالت برای استقرارهایی مناسب است که پایگاه داده به‌صورت Native روی سرور نصب و مدیریت می‌شود. مقدار `SQL_HOST` به‌طور پیش‌فرض `host.docker.internal` است و در سرویس `hse-app` نگاشت `host-gateway` تعریف شده است. در صورت نیاز، دسترسی PostgreSQL و قوانین شبکه باید طوری تنظیم شوند که اتصال از کانتینر مجاز باشد، بدون آنکه پایگاه داده به اینترنت عمومی باز شود.

**حالت B — PostgreSQL در Docker**

سرویس `postgres` در فایل Compose با پروفایل `container-db` تعریف شده است. برای اجرای این حالت، ابتدا `.env` را کامل و رمز پایگاه داده را امن کنید. سپس سرویس‌ها را با پروفایل فعال کنید:

```bash
docker compose -f docker-compose.server.yml --profile container-db up -d --build
```

در این حالت، تنظیمات اتصال برنامه باید به سرویس `postgres` در شبکه Compose اشاره کند؛ بنابراین `SQL_HOST=postgres` را در `.env` تنظیم کنید. پیش از اجرای این روش، از درست بودن پورت، نام کاربر، نام پایگاه داده و تنظیمات اتصال برنامه مطمئن شوید.

داده‌های پایگاه داده کانتینری در Volume با نام `hse_postgres_data` نگهداری می‌شوند. حذف Volume می‌تواند باعث حذف داده‌های پایگاه داده شود؛ از اجرای `docker compose down -v` در محیط عملیاتی خودداری کنید مگر آنکه حذف داده‌ها عمداً تأیید شده باشد.

### ۶. ساخت و اجرای برنامه

برای حالت PostgreSQL روی میزبان:

```bash
cd /opt/HSECORE

docker compose -f docker-compose.server.yml config -q
docker compose -f docker-compose.server.yml build
docker compose -f docker-compose.server.yml up -d
```

برای حالت PostgreSQL کانتینری، از دستور بخش قبل با `--profile container-db` استفاده کنید.

بررسی وضعیت:

```bash
docker compose -f docker-compose.server.yml ps
docker compose -f docker-compose.server.yml logs --tail=200 hse-app
```

مشاهده زنده لاگ‌ها:

```bash
docker compose -f docker-compose.server.yml logs -f hse-app
```

برای خروج از نمایش زنده لاگ‌ها، `Ctrl+C` را فشار دهید. این کار به‌خودی‌خود سرویس را متوقف نمی‌کند.

### ۷. بررسی سلامت برنامه

در فایل Compose فعلی، Health Check از این مسیر استفاده می‌کند:

```text
/api/health
```

بررسی از داخل سرور:

```bash
curl -i http://127.0.0.1:3000/api/health
```

این دستور زمانی قابل استفاده است که `APP_INTERNAL_PORT=3000` باشد و پورت روی `127.0.0.1` میزبان منتشر شده باشد. پاسخ موفق این endpoint به‌تنهایی اثبات نمی‌کند که همه ماژول‌ها، مجوزها یا گردش کارها بدون ایراد هستند؛ آزمون پذیرش جداگانه لازم است.

### ۸. اجرای مهاجرت‌های پایگاه داده

اسکریپت‌های پروژه شامل `db:migrate` و ابزار تشخیص اتصال پایگاه داده هستند:

```bash
npm run db:diagnose
npm run db:migrate
```

این دو دستور در محیط توسعه، پس از نصب وابستگی‌ها و تنظیم محیط، قابل استفاده‌اند. تصویر تولید، `server/migrate.ts` را در `dist/migrate.cjs` می‌سازد؛ اما قبل از اجرای مستقیم فایل مهاجرت داخل کانتینر تولید، رفتار آن و روش مورد انتظار پروژه را بررسی کنید.

**هشدار عملیاتی:** اسکریپت مهاجرت فعلی علاوه بر اعمال مهاجرت‌ها، تلاش‌هایی برای تکمیل ساختار جداول/ستون‌ها، ایجاد ایندکس‌ها و بررسی حساب مدیر پیش‌فرض انجام می‌دهد. آن را روی پایگاه داده عملیاتی موجود بدون نسخه پشتیبان، بررسی کد و تأیید مسئول سامانه اجرا نکنید. پیش از اجرا، تأثیر احتمالی ایجاد یا تغییر ساختار داده‌ها و فرایند ایجاد مدیر را ارزیابی کنید. از اجرای اسکریپت‌های Seed یا بازنشانی داده‌ها برای رفع خطا بدون تأیید صریح خودداری کنید.

### ۹. دسترسی از طریق دامنه و HTTPS

در پیکربندی فعلی، مقدار پیش‌فرض `DOCKER_BIND_IP` برابر `127.0.0.1` است؛ در نتیجه برنامه به‌طور پیش‌فرض فقط از همان سرور قابل دسترسی است. این رفتار برای قرار گرفتن پشت Reverse Proxy محلی مناسب است.

برای استقرار عمومی:

1. دامنه را به IP سرور هدایت کنید.
2. Nginx یا Reverse Proxy مورد تأیید را روی میزبان پیکربندی کنید.
3. گواهی TLS معتبر تهیه و تمدید خودکار آن را تنظیم کنید.
4. ترافیک HTTPS را به `127.0.0.1:3000` هدایت کنید.
5. فایروال را طوری تنظیم کنید که فقط پورت‌های لازم، مانند SSH و HTTPS، باز باشند.
6. تنظیمات CORS و URLهای عمومی برنامه را بر اساس دامنه واقعی و بدون استفاده از wildcard ناامن بررسی کنید.

**برنامه را بدون TLS در معرض شبکه‌های غیرقابل‌اعتماد قرار ندهید.** انتشار پورت روی `0.0.0.0` صرفاً برای رفع مشکل دسترسی توصیه نمی‌شود؛ ابتدا معماری Reverse Proxy و سیاست شبکه را بررسی کنید.

## پیکربندی محیطی

فایل Compose، پورت داخلی برنامه را روی `3000` تنظیم می‌کند. مسیر بارگذاری فایل‌ها در کانتینر `/app/uploads` است و به مسیر میزبان `./data/uploads` نگاشت می‌شود.

این مسیر باید در پشتیبان‌گیری لحاظ شود. قبل از تغییر مسیر یا انتقال سرور، مالکیت و مجوزهای فایل‌ها را بررسی کنید.

تنظیمات باید متناسب با محیط جدا شوند؛ برای مثال توسعه، آزمون و تولید. کلیدهای API، رمز پایگاه داده و کلید JWT نباید در کد منبع، فایل README، خروجی خطا یا commitهای Git ذخیره شوند.

## پایگاه داده و مهاجرت‌ها

HSECORE از PostgreSQL و Drizzle ORM استفاده می‌کند. پیش از هر تغییر ساختاری:

1. نسخه فعلی برنامه و پایگاه داده را ثبت کنید.
2. از پایگاه داده نسخه پشتیبان بگیرید.
3. فایل‌های مهاجرت و تغییرات schema را بررسی کنید.
4. مهاجرت را ابتدا در محیط آزمایشی اجرا کنید.
5. صحت داده‌ها و گردش‌های کاری مهم را بررسی کنید.
6. برای محیط عملیاتی، برنامه بازگشت و مسئول تأیید مشخص داشته باشید.

تغییرات ساختار داده نباید با حذف یا بازنشانی بی‌دلیل اطلاعات کاربران انجام شود. اگر برنامه از قبل داده عملیاتی دارد، راهبرد مهاجرت باید حفظ داده‌ها را در اولویت قرار دهد.

## مدیریت سرویس‌ها

دستورات زیر برای Compose فعلی هستند:

```bash
# وضعیت سرویس‌ها
docker compose -f docker-compose.server.yml ps

# لاگ آخر برنامه
docker compose -f docker-compose.server.yml logs --tail=200 hse-app

# دنبال‌کردن زنده لاگ برنامه
docker compose -f docker-compose.server.yml logs -f hse-app

# راه‌اندازی مجدد برنامه
docker compose -f docker-compose.server.yml restart hse-app

# توقف سرویس‌ها
docker compose -f docker-compose.server.yml stop

# شروع سرویس‌های متوقف‌شده
docker compose -f docker-compose.server.yml start

# توقف و حذف کانتینرها و شبکه Compose
docker compose -f docker-compose.server.yml down
```

`down` با `down -v` یکسان نیست. از `down -v` استفاده نکنید، مگر آنکه حذف Volumeها و داده‌های وابسته آگاهانه و تأیید شده باشد.

## به‌روزرسانی

پیش از به‌روزرسانی:

- نسخه و وضعیت مخزن را بررسی کنید.
- از پایگاه داده و فایل‌های بارگذاری‌شده پشتیبان بگیرید.
- تغییرات محلی و تنظیمات محیطی را بررسی کنید.
- یادداشت‌های انتشار و سازگاری مهاجرت‌ها را مطالعه کنید.

سپس نسخه تأییدشده را دریافت کنید. اگر مخزن تغییر محلی دارد، قبل از تغییر شاخه یا دریافت تغییرات، آن‌ها را بررسی و ایمن کنید:

```bash
cd /opt/HSECORE
git status
git fetch origin
```

پس از انتخاب شاخه یا commit مورد تأیید، با حفظ تغییرات محلی و فایل `.env`، تصویر جدید را بسازید و سرویس را به‌روزرسانی کنید:

```bash
docker compose -f docker-compose.server.yml config -q
docker compose -f docker-compose.server.yml build
docker compose -f docker-compose.server.yml up -d
docker compose -f docker-compose.server.yml ps
docker compose -f docker-compose.server.yml logs --tail=200 hse-app
```

اگر نسخه جدید به مهاجرت پایگاه داده نیاز دارد، آن را طبق دستورالعمل همان نسخه اجرا کنید. بازسازی تصویر یا جایگزینی کانتینر نباید به حذف Volume پایگاه داده یا فایل‌های بارگذاری‌شده منجر شود.

## پشتیبان‌گیری و بازیابی

پشتیبان‌گیری عملیاتی باید حداقل این موارد را پوشش دهد:

- پایگاه داده PostgreSQL
- فایل‌های بارگذاری‌شده در `data/uploads/`
- تنظیمات استقرار لازم برای بازیابی، با نگهداری امن اسرار
- نسخه برنامه و اطلاعات لازم برای شناسایی انتشار

برای PostgreSQL نصب‌شده روی میزبان، نمونه پشتیبان‌گیری منطقی:

```bash
pg_dump -Fc -h 127.0.0.1 -U hse_user -d hsedb \
  -f /secure-backups/hsedb.dump
```

مسیر `/secure-backups` باید از قبل ایجاد شده و دسترسی آن محدود باشد. رمز عبور را مستقیماً در فرمان قرار ندهید. نام کاربری، پایگاه داده و مقصد را با محیط واقعی تطبیق دهید.

برای پایگاه داده کانتینری، روش پشتیبان‌گیری باید با سرویس و Volume واقعی هماهنگ شود. کپی خام از فایل‌های پایگاه داده در حال اجرا، بدون روش پشتیبان‌گیری سازگار، جایگزین قابل اتکایی برای پشتیبان‌گیری PostgreSQL نیست.

بازیابی را ابتدا در محیط آزمایشی انجام دهید و صحت داده‌ها را بررسی کنید. بازیابی روی پایگاه داده عملیاتی ممکن است داده‌های موجود را جایگزین کند؛ بنابراین بدون تأیید و پشتیبان معتبر انجام نشود.

**وجود فایل پشتیبان کافی نیست؛ فرایند بازیابی نیز باید دوره‌ای آزمایش شود.**

## امنیت و حفاظت از داده‌ها

- رمز ثابت پیش‌فرض Compose را در استقرار واقعی حتماً جایگزین کنید.
- از کلید JWT قوی، محرمانه و مخصوص هر محیط استفاده کنید.
- فایل `.env` را با مجوز محدود نگهداری کنید و هرگز commit نکنید.
- پایگاه داده را در معرض اینترنت عمومی قرار ندهید.
- دسترسی کاربران و نقش‌ها را با اصل حداقل دسترسی تنظیم کنید.
- در استقرار عمومی از HTTPS و Reverse Proxy امن استفاده کنید.
- تصاویر پایه و وابستگی‌ها را به‌صورت برنامه‌ریزی‌شده به‌روزرسانی کنید.
- لاگ‌ها را برای جلوگیری از افشای اسرار و داده‌های حساس بررسی کنید.
- سیاست نگهداری، دسترسی و بازیابی پشتیبان‌ها را مستند کنید.
- برای قابلیت‌های مبتنی بر سرویس خارجی، فقط کلیدهای لازم را فعال کنید.

قواعد اتوماسیون داخلی در برنامه اجرا و در پایگاه داده اصلی نگهداری می‌شوند. برای ارتباط با سامانه‌های بیرونی، webhookها ممکن است به تنظیمات جداگانه نیاز داشته باشند. برای جلوگیری از تکرار اثرات جانبی، سامانه دریافت‌کننده نیز باید در صورت پشتیبانی، کلید idempotency ارسالی را رعایت کند.

پس از نصب یا به‌روزرسانی، آزمون‌های پذیرش زیر پیشنهاد می‌شوند:

- [ ] ورود و خروج کاربر و کنترل دسترسی‌ها آزمایش شده‌اند.
- [ ] داده ثبت‌شده پس از خروج و ورود مجدد باقی می‌ماند.
- [ ] داده‌ها از مرورگر یا نشست دیگر، مطابق سطح دسترسی، قابل مشاهده‌اند.
- [ ] کارتابل و گردش‌های ارجاع/تأیید برای کاربران مربوطه بررسی شده‌اند.
- [ ] بارگذاری و بازیابی فایل‌ها آزمایش شده‌اند.
- [ ] گزارش‌ها و خروجی‌های موردنیاز بررسی شده‌اند.
- [ ] پس از راه‌اندازی مجدد کانتینر، داده‌های پایدار باقی می‌مانند.
- [ ] نسخه پشتیبان در محیط آزمایشی بازیابی شده است.

این فهرست چک‌لیست پذیرش است، نه ادعای انجام یا موفقیت آزمون‌ها.

## عیب‌یابی

### کانتینر برنامه بالا نمی‌آید

```bash
docker compose -f docker-compose.server.yml ps
docker compose -f docker-compose.server.yml logs --tail=200 hse-app
```

خطای ساخت تصویر، متغیرهای مفقود، پورت اشغال‌شده و خطاهای شروع سرور را بررسی کنید.

### اتصال پایگاه داده برقرار نمی‌شود

- `SQL_HOST` و `SQL_PORT` را بررسی کنید.
- اگر پایگاه داده روی میزبان است، مسیر `host.docker.internal` و مجوز اتصال را بررسی کنید.
- اگر PostgreSQL کانتینری است، مطمئن شوید `SQL_HOST=postgres` تنظیم شده و پروفایل `container-db` فعال است.
- نام پایگاه داده، نام کاربری، رمز، مجوزها و تنظیمات SSL را بررسی کنید.
- از انتشار عمومی پورت پایگاه داده برای حل مشکل اتصال خودداری کنید.

### پورت برنامه در دسترس نیست

در حالت پیش‌فرض، برنامه روی `127.0.0.1` میزبان منتشر می‌شود. این رفتار برای دسترسی از طریق Reverse Proxy محلی است. ابتدا وضعیت پورت، Reverse Proxy و فایروال را بررسی کنید؛ برای رفع مشکل، بی‌درنگ پورت را روی همه رابط‌های شبکه منتشر نکنید.

### فایل‌ها پس از جایگزینی کانتینر ناپدید شده‌اند

نگاشت `./data/uploads:/app/uploads` و مسیر واقعی فایل‌ها را بررسی کنید. پیش از هر انتقال یا اصلاح، از داده‌های موجود نسخه پشتیبان بگیرید.

### پس از به‌روزرسانی خطای schema مشاهده می‌شود

نسخه برنامه، لاگ‌ها و وضعیت مهاجرت‌ها را بررسی کنید. از حذف پایگاه داده، اجرای Seed یا بازنشانی جداول برای رفع سریع خطا خودداری کنید. در صورت نیاز، مطابق برنامه بازیابی مصوب عمل کنید.

## گزارش خطا و مشارکت

برای گزارش خطا، این اطلاعات را ارائه کنید:

1. نسخه یا commit برنامه
2. محیط اجرا (توسعه یا تولید)
3. نسخه Docker و Docker Compose، در صورت مرتبط بودن
4. مراحل بازتولید خطا
5. پیام خطا و لاگ‌های مرتبط پس از حذف اسرار و اطلاعات حساس
6. نتیجه مورد انتظار و نتیجه مشاهده‌شده

رمز عبور، کلید API، JWT، داده‌های شناسایی پرسنل و اطلاعات محرمانه سازمانی را در Issueها یا گزارش‌های عمومی قرار ندهید.
